# קליטת חשבוניות — החוזה בין העמוד ל־n8n

העמוד ב־`invoices/` מחובר לוורקפלואו **Lehem veshemesh - Invoices**
(`mhKSJrTgauPv4zfN`). הכתובות בראש `invoices.js`:

```js
var BASE = 'https://shanyptr.app.n8n.cloud/webhook';
var UPLOAD_URL  = BASE + '/parse-submit';
var STATUS_URL  = BASE + '/parse-status';
var CONFIRM_URL = BASE + '/send-invoice-approval';
```

כל עוד הוורקפלואו לא פעיל, צריך להחליף `webhook` ל־`webhook-test` בשורת `BASE`.

---

## התמונה הכללית

```
דפדפן                                   n8n                        LlamaParse
  |                                       |                             |
  |-- 1. parse-submit (קובץ אחד) --------->|                             |
  |                                       |-- POST /parse/upload ------->|
  |<-- {ok, jobId} מיד ------------------- |<-- job id ------------------|
  |   (חוזר על עצמו לכל חשבונית)            |                             |
  |                                       |                             |
  |-- 2. parse-status (כל ה-jobs) -------->|                             |
  |                                       |-- GET /parse/{job} --------->|
  |<-- מצב כל אחד ------------------------ |<-- PENDING/COMPLETED -------|
  |   (כל 2 עד 5 שניות עד שכולם סופיים)     |                             |
  |                                       |                             |
  |-- 3. send-invoice-approval ----------->|                             |
  |                                       |   -> Google Sheets           |
  |<-- {ok:true} ------------------------- |                             |
```

**מי מחזיק את המצב:** הדפדפן. `jobId` חוזר אליו בשלב 1 והוא שולח אותו בחזרה
בשלב 2, ולכן n8n לא צריך לשמור שום דבר בין הקריאות. אין טבלת נתונים ואין
static data. זה יתרון אמיתי של המבנה שנבנה, ובניתי סביבו.

`invoice_id` נוצר בדפדפן ומלווה את החשבונית בכל שלוש הקריאות, כדי שהתשובות
יתאימו לשורות בלי ניחושים.

---

## 1. `parse-submit` — העלאה

`POST`, `multipart/form-data`, **קובץ אחד בכל קריאה**.

| שדה | תוכן |
|---|---|
| `file` | הקובץ, בינארי |
| `fileName` | שם הקובץ המקורי מהמכשיר |
| `invoice_id` | UUID של החשבונית |
| `batch_id` | UUID של כל הישיבה |
| `client_index` | 1, 2, 3 … |
| `client_total` | כמה קבצים באצווה |

**תשובה נדרשת:**

```json
{ "ok": true, "jobId": "..." }
```

מתקבל גם מערך עם אובייקט אחד, כמו שצומת Respond במצב `allIncomingItems`
מחזיר היום. **בלי `jobId` החשבונית מסומנת כנכשלה** ולא נסקרת, כי אין על מה
לסקור.

---

## 2. `parse-status` — סקירה

`POST`, `application/json`. הדפדפן שואל על **כל החשבוניות הפתוחות יחד**, ולא
אחת אחת. הרשימה מתכווצת ככל שחשבוניות מסתיימות.

```json
{
  "batch_id": "...",
  "jobs": [
    { "invoice_id": "...", "jobId": "..." },
    { "invoice_id": "...", "jobId": "..." }
  ]
}
```

**תשובה נדרשת** — פריט אחד לכל job, כמערך שטוח או כ־`{"invoices": [...]}`:

```json
{
  "invoice_id": "...",
  "status": "COMPLETED",
  "done": true,
  "confidence": 0.94,
  "data": {
    "supplier": "מאפיות הדר בע\"מ",
    "supplier_tax_id": "514598234",
    "invoice_number": "10427",
    "date": "2026-09-11",
    "subtotal": 420.00,
    "vat": 75.60,
    "total": 495.60
  },
  "flags": [],
  "message": null
}
```

`status` יכול לחזור בשפה של LlamaParse. העמוד מתרגם לבד:

| מ־LlamaParse | מוצג לאיריס |
|---|---|
| `PENDING`, `RUNNING` | נקראת עכשיו |
| `COMPLETED` | נקראה |
| `FAILED`, `CANCELLED` | לא נקראה |

**`data`** — שבעה שדות. `date` בפורמט `YYYY-MM-DD` כי הוא נכנס ל־`<input type="date">`.
שדה חסר מותר, הוא יוצג ריק ואיריס תמלא. גם `data` שלם חסר מותר.

`supplier_tax_id` הוא היוצא מן הכלל: הוא לא מוצג בעמוד ואי אפשר לערוך אותו.
הוא נקרא בהרצת הקריאה, והכתיבה לגיליון קורית בהרצת האישור, ולכן הדפדפן
מחזיק אותו ומחזיר אותו כמו שהוא. ספרות בלבד, בלי מקפים ובלי רווחים.

**`confidence`** — 0 עד 1. מתחת ל־0.85 הכרטיס נפתח אוטומטית.

**`flags`** — מערך של מחרוזות או של `{code, message}`. ה־`message` מוצג כמו
שהוא, ולכן צריך להיות משפט בעברית שאפשר לפעול לפיו.

**`message`** — הסבר כשנכשל.

**קצב:** כל 2 שניות, ואחרי 40 שניות כל 5. עצירה אחרי 4 ניתוקים רצופים או
12 דקות, עם כפתור "בדיקה שוב".

## 3. `send-invoice-approval` — אישור

`POST`, `multipart/form-data`, **חשבונית אחת בכל קריאה, עם הקובץ**.
נשלח בטור אחרי שאיריס אישרה. חשבוניות שנכשלו לא נכללות.

| שדה | תוכן |
|---|---|
| `file` | הקובץ, בינארי. אותה גרסה מוקטנת שנשלחה ל־`parse-submit` |
| `invoice_id` | UUID של החשבונית, זהה לזה שנשלח בשלב 1 |
| `batch_id` | UUID של הישיבה |
| `supplier` | כפי שאיריס אישרה |
| `invoice_number` | כפי שאיריס אישרה |
| `date` | `YYYY-MM-DD`, כפי שאיריס אישרה |
| `subtotal` | מספר כמחרוזת, או ריק |
| `vat` | מספר כמחרוזת, או ריק |
| `total` | מספר כמחרוזת, או ריק |
| `supplier_tax_id` | ספרות בלבד, כפי שחזר מהקריאה. איריס לא נגעה בו |
| `edited` | שמות השדות ששונו ביד, מחוברים בפסיקים. ריק אם לא נגעה |
| `client_index`, `client_total` | 1 מתוך 9 וכולי |

### למה הקובץ נשלח שוב כאן, ולמה חשבונית אחת בכל קריאה

את הקובץ מחזיק רק הדפדפן. ל־`parse-status` מגיע רק `jobId`, והבינארי אף פעם
לא היה בהרצה ההיא, ולכן צומת דרייב שם לא יעלה כלום.

מנגד, את **התאריך הנכון** אפשר לדעת רק אחרי שאיריס אישרה אותו. אם מתייקים
לפי מה שה־OCR קרא, חשבונית עם תאריך שגוי תיכנס לחודש הלא נכון ואף אחד לא
ישים לב.

הרגע היחיד שבו **גם הקובץ וגם התאריך המאושר** קיימים באותה הרצה הוא כאן.
לכן ענף הדרייב שייך למסלול הזה.

חשבונית אחת בכל קריאה, כי אז כל הרצה מטפלת בקובץ אחד ובשורה אחת, בלי
Split Out ובלי לולאה, ובלי לגעת בשאר הוורקפלואו שכבר בנוי סביב פריט בודד.

**סדר הצמתים המוצע:**

```
🌐 Webhook: קבלת נתוני חשבונית
  → Edit Fields1        שם התיקייה מהתאריך המאושר
  → Add Invoice to Sheet
  → Search files and folders   (Always Output Data דלוק)
  → If folder exists
      ├─ קיימת    → Upload Invoice
      └─ לא קיימת → Create folder → Upload Invoice
  → ↩️ תשובה · הצלחה
```

**תשובה נדרשת:** אחרי שגם השורה נכתבה וגם הקובץ עלה. העמוד מסמן חשבונית
כנשמרה רק כשחוזר `ok:true`, ולכן לחיצה חוזרת לא תיצור שורה כפולה.

```json
{ "ok": true }
```

**שים לב:** ב־multipart כל הערכים מגיעים כמחרוזות, כולל הסכומים. בצומת
Sheets כדאי להדליק `attemptToConvertTypes`, אחרת `495.6` ייכתב כטקסט
ולא כמספר, ולא יסתכם.

**המיפוי לעמודות בגיליון:**

| עמודה בגיליון | מהשדה |
|---|---|
| `Date` | `={{ $json.body.date }}` |
| `Supplier` | `={{ $json.body.supplier }}` |
| `Supplier_tax_id` | `={{ $json.body.supplier_tax_id }}` |
| `Invoice_number` | `={{ $json.body.invoice_number }}` |
| `Amount_before_vat` | `={{ $json.body.subtotal }}` |
| `Amount_after_vat` | `={{ $json.body.total }}` |
| `Service_type` | לא נאסף בעמוד |
| `Notes` | מוצע: `={{ $json.body.edited }}` |

**`edited`** — שמות השדות שאיריס שינתה ביד. ריק אומר שהיא אישרה את מה שנקרא
בלי לגעת. שווה לשמור: אחרי חודש זה אומר בדיוק אילו שדות ה־OCR טועה בהם,
ומאיזה ספק.

**שם התיקייה** ב־`Edit Fields1`:

```
={{ $json.body.date ? DateTime.fromISO($json.body.date).toFormat('yyyy-MM') : 'ללא-תאריך' }}
```

**שם הקובץ** ב־`Upload Invoice`:

```
={{ [$json.body.supplier, $json.body.invoice_number].filter(Boolean).join(' - ') || $json.body.invoice_id }}
```

מספר חשבונית לבדו לא מספיק: מספרי חשבוניות **אינם ייחודיים בין ספקים**, ושני
ספקים קטנים עם חשבונית 1043 ייצרו שני קבצים באותו שם באותה תיקייה. דרייב לא
מונע את זה, הוא פשוט שומר שניהם. הצירוף ספק ומספר הוא המינימום שגם ייחודי וגם
אפשר לסרוק בעין. התאריך ירד, כי התיקייה כבר `yyyy-MM` והיום המדויק יושב בגיליון.

`ok` חייב להיות `true` בדיוק. אחרת העמוד משאיר את החשבונית פתוחה לעריכה
ומאפשר לנסות שוב, בלי להקליד מחדש.

## הוולידציה, ומה היא באמת בודקת

`confidence` הוא לא ציון של LlamaParse. LlamaParse לא מחזיר ציון ודאות.
זה מספר שהוורקפלואו מחשב, והוא מודד **עקביות פנימית** ולא נכונות קריאה.

### בדיקות שהן באמת הצלבה

| בדיקה | מתי היא עובדת |
|---|---|
| `subtotal + vat = total` | רק כשהחשבונית מדפיסה את שלושת המספרים |
| `vat / subtotal ≈ 0.18` | אותו תנאי. 17 אחוז הוא חשבונית ישנה או ספרה שנקראה לא נכון |
| כפילות: מספר חשבונית + ספק שכבר בגיליון | תמיד. תופס צילום כפול ותופס העלאה חוזרת |
| הסכום מופיע כמחרוזת ב־markdown הגולמי | תמיד. אם הוא חושב ולא נקרא, להוריד ציון |
| ח.פ. או ע.מ., 9 ספרות עם ספרת ביקורת | כשהמספר מופיע. גם מאפשר להתאים שם ספק מרשימה במקום לסמוך על ה־OCR של השם |
| טווח מול החציון ההיסטורי של אותו ספק | אחרי כמה שבועות. פי 3 חריגה → דגל. זו הבדיקה שתופסת נקודה עשרונית במקום הלא נכון |

### מה שלא באמת נבדק

**חשבונית שמדפיסה רק סה״כ לתשלום.** אין מול מה להצליב, שום בדיקה לא נכשלת,
והציון חוזר גבוה. הציון בטוח בעצמו בדיוק איפה שיש לו הכי פחות ראיות. במקרה
הזה צריך `flag` מפורש בסגנון "יש רק סה״כ, אין מול מה להצליב".

**תאריך.** 30 יום תופס שנה שגויה, לא היפוך יום־חודש כשהיום קטן מ־13. חשבוניות
ישראליות הן dd/mm, אז זו ברירת המחדל, אבל שווה דגל כשאין שם חודש והתאריך עמום.
תאריך עתידי → דגל תמיד.

**מטבע.** כל דבר שאינו ₪ → דגל.

### ולכן

הציון לא מחליט **אם** להראות לאיריס, הוא מחליט **איך**. כל החשבוניות עוברות
במסך האישור, כי הנתונים חזרו בתשובת הסטטוס ממילא ולכן זה לא עולה אף קריאה
נוספת. ודאות גבוהה יורדת לשורה מכווצת עם הסכום בגדול. ודאות נמוכה נפתחת עם
תמונת החשבונית לצד השדות והסיבה המדויקת.

## מה יש בעמוד עצמו

- **מצלמה וגלריה בנפרד.** שדה אחד עם `capture` מסתיר בטלפון את האפשרות לבחור
  קובץ קיים, ולכן שני שדות ושני כפתורים.
- **גרירה** לתוך האזור, בדסקטופ.
- **הקטנת תמונה** לפני השליחה, 2000 פיקסל בצלע הארוכה. צילום של 8 מגה יורד
  לכ־400 קילובייט. HEIC שלא נפתח בקנבס נשלח כמו שהוא.
- **כפתור ההעלאה ננעל** לכל אורך ההעלאה והקריאה, יחד עם כפתורי הבחירה. אזהרה
  אם מנסים לסגור את הטאב באמצע.
- **חשבון חי** מתחת לשדות הסכום, שמתעדכן בהקלדה ואומר במילים אם המספרים
  מסתדרים. שדה ששונה ביד מסומן במסגרת.
- **סדר הכרטיסים** — מה שדורש עין למעלה, מה שנכשל למטה.
- **noindex** ב־head.
